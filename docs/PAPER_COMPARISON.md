# Paper Comparison Table

**Purpose.** The table compares the core papers on a common set of dimensions: name, authors,
year, tools, about, domain, pros, cons, and future work.

**Scope.** 37 papers were selected because each one either (a) audits benchmark tests, (b) builds a
verifier/test synthesizer, (c) measures reward hacking, or (d) supplies the mutation/oracle
foundations the project depends on. This is not the 1,500-record corpus; it is the set that
carries the argument.

**Evidence note.** "Pros" are the paper's own reported results, not an endorsement. "Cons" are
the paper's stated limitations where available, plus scope limits that follow from what was
evaluated. "Future work" is the paper's stated direction where the full text gives one; otherwise
it is marked *not stated*. Every number should be checked against the linked source before it is
quoted in a manuscript.

**Corpus IDs** refer to `papers/metadata/papers_research_cards.jsonl`. Evidence depth is the
label on each card (`full-text reviewed`, `full text scanned`, `abstract reviewed`,
`metadata only`).

## Comparison at a glance

This matrix records what each system actually implements and reports. "Yes" means the capability
is implemented and reported. "Partial" means it is implemented under a narrower scope.

| Capability | Probe to Generate (P0120) | UTBoost (P0001) | SWE-ABS (P0837) | MUTGEN / PRIMG (P0847/P1154) | Terminal Wrench (P0121) | AAVS (target) |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| Mutates the reference patch | Yes (semantic variants) | No | Yes (synthesized wrong patches) | Yes (function-level mutants) | No | Yes (AST operator families) |
| Detects survivors on the original suite | Yes | Yes | Yes | Yes | No | Yes |
| Synthesizes new tests against survivors | Yes | Yes | Yes | Yes | No | Yes |
| Soundness gate: gold patch must still pass | Yes (three-way filter) | Yes | Yes | Partial | n/a | Yes, explicit |
| Completeness gate: mutant must fail | Yes | Yes | Yes | Partial | n/a | Yes, explicit |
| Re-evaluates public leaderboard patches | Partial | Yes | Partial | No | No | Yes (FPFR) |
| Container / state / exit-code hacks | No | No | No | No | Yes (measurement) | Yes (Stage 2) |
| Released per-task hardened suite with provenance | No | Partial | No | No | Yes (exploits) | Target |

**Reading of the table.** The attacker → survivor → synthesizer loop is *not* new. Probe to
Generate (2026) already closes it at the test-suite level, and SWE-ABS does it with a different
generator. What this review did not find as a single system is: (1) a model-agnostic, released
hardened suite with per-task provenance; (2) one protocol that reports both false passes and
false rejections (soundness) on the gold patch; (3) the same gate applied to AST-level and
container/state-level gaming. Those three are the defensible contribution. See
[`STATE_OF_THE_FIELD.md`](STATE_OF_THE_FIELD.md).
